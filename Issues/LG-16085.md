## 🛠 Summary of changes

This is **Deploy 2** of renaming the IPP-only `same_address_as_id` string field to the boolean `ipp_current_address_matches_id`. Because the value is persisted in the encrypted session (`pii_from_user`), the rename follows the handbook's \[50/50 "rename a field"\](https://handbook.login.gov/articles/appdev-50-50.html) procedure. PR1 (Deploy 1) added the new field, wrote both, and read new-with-fallback-to-old. This PR removes the old name.

**⚠️ Deploy ordering:** This must not deploy until PR1 (Deploy 1) is in production. PR1 instances write both fields and read new-with-fallback, so during this deploy a PR1 instance can still read the field this code writes, and this code can read the field a PR1 instance wrote.

**Convert to a real boolean at the form boundary**
- `StateIdForm` and `AddressForm`: renamed the attribute to `ipp_current_address_matches_id` and cast it via `ActiveModel::Type::Boolean.new.cast` in `consume_params` (no `!!`, so `nil` — the "unanswered" state — is preserved). This matches the app's existing convention (`register_user_email_form`).
- `FormStateIdValidator`: changed `presence: true` to `inclusion: { in: \[true, false\] }`, since `false` is not "present" in ActiveModel and would otherwise be rejected.
- `state_id/show.html.erb`: radio `name:` and `checked:` now use `ipp_current_address_matches_id`.

**Remove the dual-read helper**
- Deleted `app/services/pii/current_address_matches_id.rb` and its spec. All `.read(...)` calls simplified to direct `applicant_pii\[:ipp_current_address_matches_id\]` (AAMVA/state-id-address plugins, progressive proofer, USPS applicant, result adjudicator, state ID controller).

**Remove legacy writes and log-redaction entries**
- Dropped the `same_address_as_id` writes in the state ID / address controllers and the proofing agent transformer, and the string mock values in `Idp::Constants`.
- Removed `same_address_as_id` from the log-redaction lists (`proofing_agent_job`, `dob_ssn_form`, `ssn_format_form`) and `verify_info_concern`'s `except(...)`, since the field is no longer written.

**Retain the field structurally (deprecated, not deleted)**
- Because `same_address_as_id` was persisted in production PII, it is kept as a member of `Pii::Attributes::DEPRECATED_PII_ATTRIBUTES` and in `SessionEncryptor::SENSITIVE_KEYS`. Fully removing it would cause `Pii::Attributes.new_from_hash` to silently drop the key when rehydrating existing encrypted profiles/sessions. See `pii-deprecated-attributes.md` (to be moved to the docs repo).

**Tests**
- Renamed the `same_address_as_id:` test-helper kwarg to `current_address_matches_id:` across the helpers and all call sites; updated specs to use booleans for session/PII values and strings for request-param values (mirroring what the browser submits).

Correct — which address we pass to AAMVA only affects rescue coverage (identity gate is address-independent).

Which to pass: current/edited address.

Why it rescues more: the address we need to rescue is the one IV failed on — and IV resolves the current address (it's what's used for the actual account, PhoneFinder, GPO, partner sharing). So AAMVA's :address should attest to the same current address IV checked. Passing the doc address gives you the cross-address bug (rescuing a different address than was verified); passing the current address makes the rescue value-consistent and actually valid.
